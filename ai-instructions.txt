REQUEST FLOW (HTTP):
1. Browser sends request to https://domain.com
2. Nginx receives request (reverse proxy)
3. Nginx forwards to http://localhost:3000
4. Custom server (server.ts) routes to Next.js
5. Next.js renders page (SSR) or sends static page (SSG)
6. Response returned through Nginx to browser

WEBSOCKET FLOW (Socket.IO):
1. Browser initiates WebSocket connection
2. Nginx detects ws:// upgrade headers
3. Nginx forwards upgrade to Node.js on /api/socketio
4. Socket.IO server handles on('connection')
5. Bi-directional real-time communication established


RENDERING STRATEGIES:

Server-Side Rendering (SSR):
- Home page uses dynamic content (LaserFlow with animations)
- Contact form needs form handling
- These use 'use client' directive for client-side interactivity

Static Site Generation (SSG):
- About page (mostly static content)
- Some sections pre-rendered at build time

Client-Side Rendering (CSR):
- Navigation state (active page borders)
- Form submissions
- Socket.IO connections
- Service worker registration

Lazy Loading:
- LaserFlowLazy component: Loads 3D graphics only on demand
- MeteorsLazy component: Loads meteor animation only when needed
- This improves initial page load performance


SERVICE WORKER & OFFLINE SUPPORT:

File: public/sw.js
Purpose: Enable offline functionality and intelligent caching

Caching Strategy:
- CACHE_V1: General assets cache (pages, CSS, etc.)
- API_CACHE: API response cache (network-first strategy)
- IMG_CACHE: Image cache (cache-first strategy)

How it works:
1. Service worker installed on first visit
2. Intercepts fetch requests
3. API calls: Try network first, fallback to cache
4. Images: Use cache first, fallback to network
5. Other requests: Try network first, fallback to offline page
6. When offline: Shows cached version or "offline" message

Registration: ServiceWorkerInit.tsx component registers SW on mount


CUSTOM SERVER (server.ts):

Features:
- HTTP server with Socket.IO integration
- Next.js app handler for requests
- Custom routing (skips Socket.IO requests from Next.js)
- Listens on 0.0.0.0:3000 (all interfaces)
- Socket.IO at /api/socketio path

Used for:
- Real-time features (WebSocket)
- Next.js App Router compatibility
- PM2 process management

SECTION 5: BUILD & RUN PROCESS
================================================================================

WHY THE BUILD PROCESS IS CRITICAL:
==================================

When you run "npm run build", Next.js creates the .next folder which contains:
- Compiled JavaScript optimized for production
- Pre-rendered static pages
- Processed CSS from Tailwind (tree-shaking unused styles)
- Minified and bundled code
- Source maps for debugging
- Asset optimization (images, fonts, etc.)

WITHOUT "npm run build":
- The app is just source code (TypeScript, JSX)
- Browsers can't run TypeScript directly
- Styles aren't compiled from Tailwind syntax
- Animations and 3D graphics aren't bundled
- Service worker has nothing to cache

This is why offline functionality breaks without the build step.
The service worker tries to cache source files, not the compiled output.


DEVELOPMENT PROCESS:
====================

1. Start development server:
   npm run dev

   - Runs nodemon which watches src/ folder
   - Restarts on file changes
   - Runs custom server.ts
   - Next.js app available at http://localhost:3000
   - Hot reload for most changes (some require full restart)

2. Make changes to files:
   - .tsx files: React components
   - .css files: Styles (Tailwind + custom)
   - .ts files: Utilities, data, config
   - Changes auto-reload in browser

3. Test changes:
   - Open browser to http://localhost:3000
   - Navigate to pages
   - Test interactions, forms, animations
   - Check console for errors (F12)
   - Check Network tab for API calls

4. Run linting (optional):
   npm run lint
   - Checks code quality
   - Identifies potential issues

5. Stop development server:
   Press Ctrl+C in terminal

FORM PATTERNS:

Using React Hook Form + Zod:
import { useForm } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { z } from 'zod'

const schema = z.object({
  email: z.string().email(),
  message: z.string().min(10),
})

export function ContactForm() {
  const { register, handleSubmit, formState: { errors } } = 
    useForm({ resolver: zodResolver(schema) })
  
  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register('email')} />
      {errors.email && <span>{errors.email.message}</span>}
    </form>
  )
}

SECTION 8: COMMON DEBUGGING APPROACHES
================================================================================

PROBLEM: App doesn't build
SOLUTION:
1. Check error message carefully (usually tells you what's wrong)
2. Try: npm install (dependencies might be broken)
3. Check TypeScript errors: npm run lint
4. Look for missing imports or syntax errors
5. Check tsconfig.json for path mappings

PROBLEM: Page loads but styling looks wrong
SOLUTION:
1. Check browser DevTools → Elements tab
2. Look at applied Tailwind classes
3. Check if CSS is being loaded (Network tab → CSS file)
4. Hard refresh browser: Ctrl+Shift+R (Windows) or Cmd+Shift+R (Mac)
5. Clear .next folder and rebuild: npm run build

PROBLEM: Animation is choppy or slow
SOLUTION:
1. Check if animation is in lazy component (defer loading)
2. Use Chrome DevTools → Performance tab
3. Check memory usage: top command
4. Reduce animation complexity
5. Use will-change CSS for performance: will-change: transform

PROBLEM: Images not loading
SOLUTION:
1. Check image path in public/ folder
2. Verify Image component is used (Next.js optimization)
3. Check alt text is provided
4. Ensure width/height are set for Image component
5. Check network requests for 404 errors

PROBLEM: Form submission not working
SOLUTION:
1. Check browser console for errors (F12)
2. Check Network tab → see if POST request is sent
3. Verify form validation schema (Zod)
4. Check server endpoint exists
5. Look at server logs for errors

PROBLEM: Socket.IO connection not working
SOLUTION:
1. Check browser console for WebSocket errors
2. Verify /api/socketio path is correct
3. Check server logs: pm2 logs turab-root
4. Ensure server.ts is running
5. Check firewall allows WebSocket (port 3000)

PROBLEM: Service worker not registering
SOLUTION:
1. Check if /public/sw.js exists
2. Verify browser console in DevTools
3. Check Application tab → Service Workers
4. Clear all storage and reload (DevTools → Application → Clear Storage)
5. Check if HTTPS is being used (required for production)

PROBLEM: Database operations fail
SOLUTION:
1. Check DATABASE_URL in .env.local
2. Verify Prisma client is generated: npx prisma generate
3. Check schema in prisma/schema.prisma
4. Try: npx prisma db push
5. View database: npx prisma studio

DEBUGGING TOOLS:
- Browser DevTools (F12): Inspect elements, check console, network
- VS Code: Set breakpoints in .tsx files
- PM2 logs: pm2 logs turab-root
- Network tab: Monitor API calls and WebSocket
- Performance tab: Check rendering performance
- Lighthouse: Check accessibility and performance scores

SECTION 10: IMPORTANT TECHNICAL DETAILS
================================================================================

WHY TYPESCRIPTIGNORE IS SET:

next.config.ts contains:
  typescript: { ignoreBuildErrors: true }

This allows:
- TypeScript errors don't block production builds
- Useful during development when types might not be perfect
- Can be removed once TypeScript is strict throughout

Impact:
- Build succeeds even with TS errors
- Errors still show in IDE and console
- Not recommended for production
- Should be removed for strict type safety


WHY REACTSTRICTMODE IS DISABLED:

next.config.ts contains:
  reactStrictMode: false

Normally React Strict Mode:
- Double-invokes components in development
- Helps find bugs in useEffect cleanup
- But causes double rendering issues here

Why disabled:
- Custom server setup might conflict
- Development was cleaner without it
- Can be enabled once issues are resolved


WEBPACK CONFIGURATION:

Disables hot module replacement to use nodemon instead:
- Nodemon watches server.ts
- Triggers full restart on changes
- Cleaner than HMR in this setup
- Good for custom server development

SECTION 11: DEPLOYMENT CONTEXT
================================================================================

When deploying to VPS:

1. CRITICAL: npm run build MUST be done
   - Creates .next folder with all compiled code
   - Without this, nothing works

2. Service worker MUST be served at /sw.js
   - Nginx needs to proxy /sw.js correctly
   - Browser must be able to fetch it

3. Environment variables MUST be set
   - Create .env.local on VPS
   - DATABASE_URL must point to correct database
   - NODE_ENV must be "production"

4. PM2 manages the process
   - pm2 start npm --name "turab-root" -- start
   - Keeps app running even if it crashes
   - Auto-restarts on server reboot

5. Nginx acts as reverse proxy
   - Listens on ports 80 and 443 (HTTP/HTTPS)
   - Forwards traffic to Node.js on port 3000
   - Serves static files efficiently
   - Handles SSL certificates

For complete deployment guide, see DEPLOYMENT_GUIDE.txt
